# Plan: 质量抽样上限 1000 + 高性能候选抽样（避免 N 次 DB 循环）

## Goal
- 将“质量抽样数量（quality_samples）”上限从 20 提升到 1000，并确保在大图库（40~50 万）与高并发场景下仍保持稳定、低延迟。
- 质量优先策略在大抽样数下不再触发“循环 N 次 pick_random_image 的 DB 查询风暴”，改为少量（≤2 次）批量查询获取候选，再在内存中评分挑选。

## Scope
- In:
  - 后端：/random 的 quality_samples 校验范围调整（1~1000），并优化 quality 策略为批量候选抽样
  - 后端：/admin/settings 对 random.quality_samples 的校验范围调整（1~1000）
  - 前端：推荐策略页/系统设置页/随机调试页的质量抽样输入上限调整（1000）与文案更新
  - 测试：更新 random 质量策略单测以匹配新抽样逻辑，并补齐边界验证
- Out:
  - 引入新的持久化“质量分数”列或离线索引（本轮先做“批量抽样 + 评分挑选”）

## Assumptions / Dependencies
- `images.random_key` 已有索引（现有 `idx_images_filter` 等），可用 “random_key >= r + LIMIT N + wrap-around” 做高性能抽样。

## Phases
1. 后端：实现 QLT-1100（批量抽样 + 上限 1000），更新单测并通过
2. 前端：实现 UI-1101（输入上限 + 文案），跑 vitest/typecheck 并通过
3. 回归：运行 `scripts/test_all.ps1`，更新 Issue CSV 状态并 push
